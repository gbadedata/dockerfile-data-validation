# Data governance

## What is recorded, and where

| Question | Answer lives in |
|---|---|
| Which dataset is in this image? | `io.gbadedata.dataset.*` labels; `dataset` in `/app/reports/manifest.json` |
| Where did it come from, under what licence? | `data/dataset.yaml` (upstream repository, commit and path), `dataset.licence` label |
| Which rules was it checked against? | `io.gbadedata.schema.*` labels; the contract file shipped in `/app/contracts/` |
| Which rows were set aside, and why? | `/app/reports/quarantine.csv`: original values, line number and reason codes |
| How good is the model, measured how? | `/app/reports/model.json` (re-scored metrics); `/app/model/model_card.json` |
| Has anything changed since the build? | `docker run --rm IMAGE` re-hashes every shipped file against the manifest |

## Ownership and change control

- **Data contract** (`contracts/penguins.v1.yaml`): a change to a rule changes
  the file's hash, and so the `schema.sha256` label. Loosening a rule (wider
  range, higher quarantine limit) is a minor version bump; removing or renaming
  a column is a major one, and the model contract's lineage check then fails
  until the model is retrained under the new version.
- **Model contract** (`contracts/model.v1.yaml`): thresholds can only be lowered
  in a reviewed change. The model card cannot lower them: the gate re-scores
  the model itself.
- **Dataset record** (`data/dataset.yaml`): updating the data means updating the
  pinned upstream commit, the file and its hash together. A file that does not
  match its record fails the build.
- **Label standard** (`standards/labels.v1.yaml`): versioned, and that version is
  itself a required label.

## Quarantine policy

Quarantined rows are never deleted. They ship inside the image with their
reasons, so a downstream user can see exactly what was excluded. If the
quarantined share passes the contract's limit (2% here), the build fails
instead: at that point the delivery is suspect, and the fix belongs upstream.

## Reproducibility

- Runtime dependencies are pinned in `requirements.lock`; training dependencies
  in `requirements-train.lock`.
- The model is stored as rounded JSON parameters. CI retrains it and fails if
  the result is not byte-identical to the committed artefact.
- The broken fixtures are generated by `fixtures/make_fixtures.py`; CI
  regenerates them and fails if they drift.

## What this does not prove

Labels and the manifest prove that an image is **consistent** with itself: the
labels describe the files inside, and the files passed the gates. They do not
prove **who** built it. Anyone who can run the build can produce a
self-consistent image. Signing the image (for example with cosign) and
attaching build provenance attestations would close that gap, and are the next
step.
